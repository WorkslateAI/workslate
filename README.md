# Workslate AI: Landing Page SPA

A responsive, vector-first React single page application that presents **Workslate AI**, an AI-powered platform for **financial orchestration**: intelligent ledger reconciliation and programmable B2B token movement across **EVM-compatible blockchains**.

Built with **GitHub Spec Kit** (spec-driven development). The spec is the source of truth and the code is generated and verified against it.

## 1. Purpose

- Present Workslate AI's value proposition: *"Reconcile First. Move Value with Confidence."*
- Explain four capabilities: multi-party ledger reconciliation, corporate wallet orchestration, programmable settlement rules, and end-to-end transaction traceability.
- Rank for the topics **blockchain, EVM, Web3j, Web3 and P2P workflows** through SEO-optimized, semantic components.
- Meet a **Lighthouse score of 95+** in Performance, Accessibility, Best Practices and SEO.
- Demonstrate a reusable, spec-driven component architecture.

## 3. Overview

### Page sections (each a reusable component)

- **Header**: logo, nav (Home, How It Works, Global, Docs, Features dropdown), Register for demo CTA, mobile menu
- **Hero**: eyebrow, h1 "Reconcile First. Move Value with Confidence.", typing AI prompt chip, CTAs, market network image
- **Business Problem**: the reconciliation gap with a pain-point card
- **How It Works**: four P2P workflow steps (obligation → reconciliation → authorization → on-chain movement) with a video placeholder
- **Global**: Seamless / Secure / Global cards plus a world banner image
- **Features**: four cards — Multi-Party Ledger Reconciliation, Corporate Wallet Orchestration, Programmable Settlement Rules, End-to-End Transaction Traceability — with a sticky sidebar nav
- **Prompt**: AI prompt chip and typing "Ask Workslate AI" response (`AITextRenderer`)
- **Docs** (`#/docs` hash route): Web3j / BPMN / EVM architecture field guide with search
- **Footer**

### Technical approach

| Area | Decision |
|------|----------|
| Framework | React 18+, TypeScript, Vite |
| Styling | Tailwind CSS v4 with design tokens, mobile-first; `overflow-x: clip` on html/body guarantees no horizontal scrolling at any viewport |
| Graphics | Inline SVG icons/logo; optimized raster illustrations (AVIF/WebP/JPEG srcset at 480/768/1200w) |
| Reuse | atoms → molecules → sections; content in `src/content/*.ts` |
| SEO | Helmet metadata, JSON-LD (Organization, SoftwareApplication, FAQPage), prerendered HTML, sitemap.xml, robots.txt |
| Performance | Code-splitting, self-hosted font subset, inline critical CSS, no heavy libraries |
| Testing | Vitest, Playwright (responsive), axe (a11y), Lighthouse CI |

### SEO keyword targets

`blockchain` · `EVM` · `EVM-compatible nodes` · `Web3j` · `Web3j Java integration` · `P2P workflows` · `peer-to-peer token transfer` · `multi-chain token tracking` · `Web3`

Use each naturally in headings, body copy, SVG `<title>`/`aria-label` text and metadata. Avoid keyword stuffing.

## 4. Execution Steps (Spec-Driven Workflow)

**Prerequisites:** Python 3.11+, [uv](https://docs.astral.sh/uv/), Git, Node.js 20+, and an AI coding agent (Claude Code, GitHub Copilot, Gemini CLI, etc.).

### Step 1: Install Spec Kit and initialize

```bash
uv tool install specify-cli --from git+https://github.com/github/spec-kit.git
specify init workslate-spa --ai claude
cd workslate-spa
mkdir design   # place the reference screenshot at design/Workslate–SinglePage.png
```

### Step 2: Run the commands in your agent

| Command | Purpose | Output |
|---------|---------|--------|
| `/speckit.constitution` | Project principles (React SPA, vector-first, Lighthouse 95+, SEO, a11y) | `.specify/memory/constitution.md` |
| `/speckit.specify` | What to build: sections, copy, keywords, acceptance criteria | `specs/<feature>/spec.md` |
| `/speckit.clarify` | Resolve open questions (Web3j support, links, domain) | Refined spec |
| `/speckit.plan` | Tech stack and component architecture | `plan.md`, `research.md`, `data-model.md`, `contracts/`, `quickstart.md` |
| `/speckit.tasks` | Dependency-ordered task list | `tasks.md` |
| `/speckit.analyze` | Consistency check across spec, plan and tasks | Report |
| `/speckit.implement` | Build the application | Source code |

### Step 3: Verify and iterate

If something is off, update the **spec or plan first**, then re-run `/speckit.tasks` and `/speckit.implement`. The spec stays the source of truth.

## 5. Running Locally

```bash
# 1. Clone
git clone https://github.com/<your-org>/workslate-spa.git
cd workslate-spa

# 2. Install dependencies
npm install

# 3. Start the dev server (hot reload)
npm run dev
# → http://localhost:5173

# 4. Production build and preview (use this for performance checks)
npm run build
npm run preview
# → http://localhost:4173
```

### Useful scripts

| Script | Description |
|--------|-------------|
| `npm run dev` | Development server |
| `npm run build` | Type-check, build and prerender |
| `npm run preview` | Serve the production build |
| `npm test` | Vitest unit tests |
| `npm run test:e2e` | Playwright responsive and accessibility tests |
| `npm run lighthouse` | Lighthouse CI against the production build |
| `npm run check:js-budget` | Fails if production JS exceeds 100 KB gzip |

### Check Lighthouse locally

```bash
npm run build && npm run preview
npx lighthouse http://localhost:4173 --view                    # mobile
npx lighthouse http://localhost:4173 --preset=desktop --view   # desktop
```

> Always audit the **production build**, not the dev server, because dev builds are unminified and will score lower.

## 6. Going Live

Any static host works because the build output is prerendered static files in `dist/`.

### Option A: GitHub Pages (GitHub Actions)

1. In the repo, go to **Settings → Pages → Source: GitHub Actions**.
2. Set `base` in `vite.config.ts` to `/<repo-name>/` (skip this for a custom domain).
3. Add `.github/workflows/deploy.yml`:

```yaml
name: Deploy
on:
  push:
    branches: [main]
permissions:
  contents: read
  pages: write
  id-token: write
jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with: { node-version: 20, cache: npm }
      - run: npm ci
      - run: npm run build
      - run: npm run lighthouse    # fails the deploy if any score < 0.85
      - uses: actions/upload-pages-artifact@v3
        with: { path: dist }
  deploy:
    needs: build
    runs-on: ubuntu-latest
    environment: { name: github-pages }
    steps:
      - uses: actions/deploy-pages@v4
```

### Option B: Vercel or Netlify

- Import the GitHub repo.
- Build command: `npm run build`. Output directory: `dist`.
- Add your custom domain and enable HTTPS.

**Deploy hook (CI-triggered deploys):** in Vercel, go to **Project Settings →
Git → Deploy Hooks** and create a hook for the `main` branch. Save its URL as
the `VERCEL_DEPLOY_HOOK_URL` secret in **GitHub → Settings → Secrets and
variables → Actions**. The `CI` workflow POSTs to it after unit tests, the
production build, the JS budget check, and Playwright E2E tests pass on pushes
to `main`, so deployments only ship when CI is green. If the secret is not set,
the step skips without failing CI. If you keep Vercel's GitHub-connected
auto-deploys enabled, the hook is unnecessary.

### Post-deploy checklist

- [ ] Canonical URL, Open Graph URL and `sitemap.xml` use the live domain
- [ ] `robots.txt` allows crawling
- [ ] Submit the sitemap to Google Search Console and Bing Webmaster Tools
- [ ] Validate JSON-LD with the Rich Results Test
- [ ] Run Lighthouse (mobile) against the live URL: **90+ on all four categories**
- [ ] Share the link to confirm the Open Graph preview renders

## 7. Quality Gates

| Metric | Target |
|--------|--------|
| Lighthouse Performance / Accessibility / Best Practices / SEO | ≥ 90 target, ≥ 85 CI gate (mobile) |
| Largest Contentful Paint | < 2.0 s |
| Cumulative Layout Shift | < 0.05 |
| Total Blocking Time | < 150 ms |
| JavaScript (gzip) | < 100 KB |
| Accessibility | WCAG AA, zero axe violations |

CI blocks merges and deploys that fall below these targets.

## 9. Contributing

1. Change the **spec** first (`specs/<feature>/spec.md`), then the plan and tasks.
2. Reuse existing components before creating new ones.
3. Keep every illustration as inline SVG with a `<title>` and `aria-label`.
4. Run `npm test && npm run test:e2e && npm run lighthouse` before opening a PR.
