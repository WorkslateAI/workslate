03 / Vocabulary

Core terminology

Web3jJava SDK

Java integration library for Ethereum JSON-RPC, ABI encoding, contract wrappers, transaction submission and event/log access.

Java → JSON-RPC → node
BPMNProcess model

Business Process Model and Notation: tasks, gateways, events, timers, message flows and error paths that describe a process.

Sequence · gateway · event
OrchestrationCoordination

A central process instance controls which step runs next, records progress and manages retries, waits and compensating actions.

Process instance
Off-chainExternal systems

Work outside the blockchain, such as identity checks, pricing, banking APIs, databases or private business data.

API · database · worker
On-chainLedger

Transactions, smart-contract execution, logs and state transitions recorded or validated by the blockchain protocol.

Transaction → state transition
EVMExecution

Ethereum Virtual Machine: deterministic execution environment for smart-contract bytecode, subject to gas and protocol rules.

Bytecode · gas · opcodes
ConsensusAgreement

Protocol by which network participants agree on block ordering and canonical chain history. Mechanisms differ by network: e.g. proof of stake or QBFT.

Ordering · validity · finality
StateCurrent facts

Current account balances, nonces, contract storage and code, as defined by a particular block. State changes through valid execution.

Account + contract state
StorageContract data

Persistent smart-contract key/value slots. Distinct from memory (temporary during execution) and calldata (input data).

storage · memory · calldata
Transaction receiptExecution result

Post-inclusion metadata such as status, gas used, block reference and emitted logs. A submitted hash alone does not prove success.

hash → receipt → verify status
P2P networkCommunication

Peer-to-peer communication between nodes to discover peers and exchange protocol messages, transactions and blocks.

Peers · gossip · discovery
Node / validatorNetwork role

A node runs client software and validates or relays data. A validator has additional consensus duties where the network design requires it.

Execution client ≠ validator in every design
Block + finalityChain history

A block groups ordered transactions. Finality is the protocol's assurance that a block will not be reverted under stated assumptions.

Inclusion ≠ immediate finality
IdempotencyReliability

Repeated delivery or retry should not cause the same business effect twice. Use stable business IDs and on-chain replay protections.

Idempotency key · unique operation
Saga / compensationRecovery

A sequence of local transactions with compensating business actions when later steps fail. Compensation is not a blockchain rollback.

Forward action ↔ compensation
Event / logObservability

Smart contracts emit logs that applications can query or subscribe to. Treat them as signals to verify against canonical chain data.

Event → listener → workflow
NonceTransaction order

For an externally owned Ethereum account, a sequential transaction counter that helps enforce ordering and prevent replay of the same transaction.

Account nonce · pending tx
RPC endpointNode interface

An interface, commonly JSON-RPC over HTTP or WebSocket, through which an application asks a node for data or submits transactions.

eth_call · eth_sendRawTransaction
04 / Lifecycle

Example: orchestrate a token transfer

A BPMN process can span minutes or days even though contract execution is a discrete transaction.
Start + validate

Receive transfer request. Validate wallet, business limits, identity and sanctions using off-chain services.

Prepare transaction

Java worker uses Web3j to encode contract call, estimate gas and manage signer / nonce policy.

Submit + wait

Submit signed transaction to an RPC node. Persist transaction hash and move BPMN instance to a durable wait state.

Confirm execution

Poll or consume events, retrieve receipt, check status and apply network-specific confirmation / finality policy.

Reconcile + finish

Update off-chain records idempotently. On failure, retry safely or start a defined compensation / manual review path.

05 / Example interaction

Illustrative Java + Web3j flow

// Conceptual flow only — configure provider, signer and contract wrapper securely.
Web3j web3 = Web3j.build(new HttpService(rpcUrl));

// 1. Submit a contract method through a generated / loaded wrapper.
TransactionReceipt receipt = tokenContract.transfer(recipient, amount).send();

// 2. Verify execution; a mined transaction can still fail.
if (!receipt.isStatusOK()) {
  // BPMN error path: retry only if safe, compensate, or route to review.
  throw new IllegalStateException("On-chain execution failed");
}

// 3. Persist tx hash + block reference, then reconcile business state idempotently.
String txHash = receipt.getTransactionHash();
// Production: consider async submission, receipt polling, confirmations/finality,
// duplicate events, reorg handling, key custody, gas and nonce coordination.

The snippet is illustrative and assumes a compatible contract wrapper and APIs. In production, avoid blocking a workflow worker for long confirmation waits; persist the hash and resume the process from a message, timer or job.

06 / Design decisions

Reliability rules of thumb

Separate responsibilities

BPMN owns business progression. Java/Web3j owns node integration. Smart contracts own on-chain invariants. Consensus belongs to the network protocol.

Assume asynchronous outcomes

A successful RPC submission is not the same as inclusion, and inclusion is not always finality. Model submitted, included, confirmed, failed and replaced states explicitly.

Design for duplicates

Workers retry; events may be replayed; processes may restart. Use idempotent handlers, unique operation IDs, contract-level safeguards and reconciliation.

Protect keys and privacy

Keep private keys out of BPMN variables and logs. Use a signer / custody boundary. Put sensitive personal or commercial data off-chain where appropriate.

Know the network model

Consensus, finality, permissioning and validator roles depend on the chosen chain. Public Ethereum and a permissioned QBFT network are not interchangeable.

Make recovery explicit

Define timeout, transaction replacement, reorg, contract revert, low gas, RPC outage, manual review and compensation paths before production.

07 / Clarifications

Common misconceptions

Does BPMN execute smart contracts?

No. BPMN defines the process and invokes workers or services. A Java worker may use Web3j to interact with a node, which processes the transaction according to the chain's protocol.

Is blockchain storage the same as transaction history?

No. Contract storage is part of current world state. Transaction history, receipts and logs describe activity that led to state changes. Node implementations may prune or archive different data, so data availability should be planned.

Does P2P networking equal consensus?

No. P2P transports messages among nodes. Consensus rules determine how participants agree on block ordering and finality. Networking supports consensus but does not define it by itself.

Can an off-chain database transaction be rolled back by the EVM?

No. The database and blockchain have separate transaction boundaries. Use a saga-style process, explicit compensating actions and reconciliation to handle partial completion.

Where should workflow state live?

Store process progress and operational metadata in the workflow engine and supporting application store; keep the authoritative on-chain facts in the contract / chain. Persist transaction hashes and enough metadata to resume and reconcile after restarts.
